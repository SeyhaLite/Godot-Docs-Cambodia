# 3.ការរៀបចំឆាក

អត្ថបទនេះគ្របដណ្តប់លើប្រធានបទដែលពាក់ព័ន្ធនឹងការរៀបចំខ្លឹមសារឆាក (scene content) ប្រកបដោយប្រសិទ្ធភាព។ តើអ្នកគួរប្រើ `nodes` អ្វីខ្លះ? តើអ្នកគួរដាក់ពួកវានៅឯណា? តើពួកវាគួរធ្វើអន្តរកម្មគ្នាយ៉ាងដូចម្តេច?

## របៀបបង្កើតទំនាក់ទំនងប្រកបដោយប្រសិទ្ធភាព[](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html#how-to-build-relationships-effectively)

នៅពេលដែលអ្នកប្រើប្រាស់ Godot ចាប់ផ្តើមបង្កើតឆាកផ្ទាល់ខ្លួនរបស់ពួកគេ ពួកគេតែងតែជួបប្រទះនឹងបញ្ហាដូចខាងក្រោម៖

ពួកគេបង្កើតឆាកដំបូងរបស់ពួកគេ និងបំពេញវាដោយខ្លឹមសារ រួចទីបំផុតបញ្ចប់ដោយការរក្សាទុកមែកធាង (branches) នៃឆាករបស់ពួកគេទៅជាឆាកដាច់ដោយឡែក ខណៈដែលអារម្មណ៍រំខានដែលថាពួកគេគួរតែបំបែកអ្វីៗចេញពីគ្នាចាប់ផ្តើមកកើនឡើង។ ទោះជាយ៉ាងណាក៏ដោយ ពួកគេបន្ទាប់មកកត់សម្គាល់ឃើញថាការយោងដ៏រឹងមាំ (hard references) ដែលពួកគេអាចពឹងផ្អែកលើមុននេះ លែងអាចធ្វើទៅបានទៀតហើយ។ ការប្រើឆាកឡើងវិញនៅកន្លែងច្រើនបង្កើតបញ្ហា ព្រោះថាផ្លូវ `node` (node paths) មិនអាចរកគោលដៅរបស់ពួកវាឃើញ ហើយការតភ្ជាប់សញ្ញា (signal connections) ដែលបានបង្កើតនៅក្នុងកម្មវិធីនិពន្ធ (editor) ត្រូវបានបំបែក។

ដើម្បីដោះស្រាយបញ្ហាទាំងនេះ អ្នកត្រូវបង្កើតឧទាហរណ៍ (instantiate) នៃឆាករង (sub-scenes) ដោយមិនឱ្យពួកវាត្រូវការព័ត៌មានលម្អិតអំពីបរិស្ថានរបស់ពួកវា។ អ្នកត្រូវអាចទុកចិត្តថាឆាករងនឹងបង្កើតខ្លួនវាដោយមិនជ្រើសរើសថាតើវាត្រូវបានប្រើប្រាស់យ៉ាងដូចម្តេច។

អ្វីមួយដែលសំខាន់បំផុតដែលត្រូវពិចារណាក្នុង `OOP` គឺការរក្សា `classes` ដែលមានគោលបំណងតែមួយ និងផ្តោតលើការងារ ជាមួយនឹង [loose coupling](https://en.wikipedia.org/wiki/Loose_coupling) ទៅនឹងផ្នែកផ្សេងទៀតនៃមូលដ្ឋានកូដ (codebase)។ វារក្សាទំហំនៃវត្ថុ (objects) ឱ្យតូច (សម្រាប់ភាពងាយស្រួលក្នុងការថែរក្សា) និងកែលម្អភាពអាចប្រើឡើងវិញរបស់ពួកវា។

ការអនុវត្តល្អបំផុតរបស់ `OOP` ទាំងនេះមានផលប៉ះពាល់ _ជាច្រើន_ ចំពោះការអនុវត្តល្អបំផុតនៅក្នុងរចនាសម្ព័ន្ធឆាក និងការប្រើប្រាស់ស្គ្រីប។

**ប្រសិនបើអាចធ្វើទៅបាន អ្នកគួរតែរចនាឆាកឱ្យគ្មានការពឹងផ្អែក (dependencies)។** មានន័យថា អ្នកគួរបង្កើតឆាកដែលរក្សាអ្វីៗទាំងអស់ដែលពួកវាត្រូវការនៅក្នុងខ្លួនពួកវាផ្ទាល់។

ប្រសិនបើឆាកមួយត្រូវធ្វើអន្តរកម្មជាមួយបរិបទខាងក្រៅ អ្នកអភិវឌ្ឍន៍ដែលមានបទពិសោធន៍ណែនាំឱ្យប្រើប្រាស់ [Dependency Injection](https://en.wikipedia.org/wiki/Dependency_injection)។ បច្ចេកទេសនេះពាក់ព័ន្ធនឹងការឱ្យ `API` កម្រិតខ្ពស់ផ្តល់នូវការពឹងផ្អែក (dependencies) របស់ `API` កម្រិតទាប។ ហេតុអ្វីបានជាត្រូវធ្វើបែបនេះ? ព្រោះថា `classes` ដែលពឹងផ្អែកលើបរិស្ថានខាងក្រៅរបស់ពួកវា អាចបណ្តាលឱ្យកើតមានកំហុស (bugs) និងអាកប្បកិរិយាដែលមិនបានរំពឹងទុកដោយចៃដន្យ។

ដើម្បីធ្វើបែបនេះ អ្នកត្រូវបញ្ចេញទិន្នន័យ ហើយបន្ទាប់មកពឹងផ្អែកលើបរិបទមេ (parent context) ដើម្បីចាប់ផ្តើម (initialize) វា៖

1.  តភ្ជាប់ទៅនឹងសញ្ញា (signal)។ មានសុវត្ថិភាពខ្លាំងណាស់ ប៉ុន្តែគួរប្រើតែដើម្បី "ឆ្លើយតប" (respond) ចំពោះអាកប្បកិរិយាប៉ុណ្ណោះ មិនមែនដើម្បីចាប់ផ្តើមវានោះទេ។ តាមទម្លាប់ ឈ្មោះសញ្ញាជាធម្មតាគឺជាពាក្យកិរិយាអតីតកាលដូចជា "entered", "skill\_activated", ឬ "item\_collected"។

    ```
    # Parent
    $Child.signal_name.connect(method_on_the_object)

    # Child
    signal_name.emit() # Triggers parent-specified behavior.
    ```
2.  ហៅ `method`។ ប្រើដើម្បីចាប់ផ្តើមអាកប្បកិរិយា។

    ```
    # Parent
    $Child.method_name = "do"

    # Child, assuming it has String property 'method_name' and method 'do'.
    call(method_name) # Call parent-specified method (which child must own).
    ```
3.  ចាប់ផ្តើម (Initialize) លក្ខណៈសម្បត្តិ [Callable](https://docs.godotengine.org/en/stable/classes/class_callable.html#class-callable)។ មានសុវត្ថិភាពជាង `method` ព្រោះមិនចាំបាច់មានកម្មសិទ្ធិលើ `method` នោះទេ។ ប្រើដើម្បីចាប់ផ្តើមអាកប្បកិរិយា។

    ```
    # Parent
    $Child.func_property = object_with_method.method_on_the_object

    # Child
    func_property.call() # Call parent-specified method (can come from anywhere).
    ```
4.  ចាប់ផ្តើម (Initialize) ការយោង `Node` ឬ `Object` ផ្សេងទៀត។

    ```
    # Parent
    $Child.target = self

    # Child
    print(target) # Use parent-specified node.
    ```
5.  ចាប់ផ្តើម (Initialize) `NodePath`។

    ```
    # Parent
    $Child.target_path = ".."

    # Child
    get_node(target_path) # Use parent-specified NodePath.
    ```

ជម្រើសទាំងនេះលាក់ចំណុចចូលប្រើ (points of access) ពី `node` កូន។ នេះជាការបន្តរក្សាឱ្យកូន **loosely coupled** ជាមួយបរិស្ថានរបស់វា។ អ្នកអាចប្រើវាឡើងវិញនៅក្នុងបរិបទផ្សេងទៀតដោយមិនមានការផ្លាស់ប្តូរបន្ថែមទៀតទៅលើ `API` របស់វា។

> **ចំណាំ** ទោះបីជាឧទាហរណ៍ខាងលើបង្ហាញពីទំនាក់ទំនងមេ-កូន (parent-child) ក៏ដោយ គោលការណ៍ដូចគ្នាក៏អនុវត្តចំពោះទំនាក់ទំនងវត្ថុទាំងអស់ផងដែរ។ `Nodes` ដែលជាបងប្អូន (siblings) គួរតែដឹងតែពីលំដាប់ថ្នាក់ (hierarchies) ផ្ទាល់ខ្លួនរបស់ពួកគេប៉ុណ្ណោះ ខណៈដែលបុព្វបុរស (ancestor) ធ្វើជាអ្នកសម្របសម្រួលការទំនាក់ទំនង និងការយោងរបស់ពួកគេ។
>
> ```
> # Parent
> $Left.target = $Right.get_node("Receiver")
>
> # Left
> var target: Node
> func execute():
> 	# Do something with 'target'.
>
> # Right
> func _init():
> 	var receiver = Receiver.new()
> 	add_child(receiver)
> ```

គោលការណ៍ដូចគ្នាក៏អនុវត្តចំពោះវត្ថុដែលមិនមែនជា `Node` ដែលរក្សាការពឹងផ្អែកលើវត្ថុផ្សេងទៀតផងដែរ។ វត្ថុណាមួយដែលជាកម្មសិទ្ធិរបស់វត្ថុផ្សេងទៀត គួរតែគ្រប់គ្រងទំនាក់ទំនងរវាងពួកវា។

> **ការព្រមាន** អ្នកគួរតែពេញចិត្តក្នុងការរក្សាទិន្នន័យនៅក្នុងផ្ទះ (ខាងក្នុងឆាក) ទោះជាយ៉ាងណាក៏ដោយ ព្រោះការដាក់ការពឹងផ្អែកលើបរិបទខាងក្រៅ ទោះបីជា loosely coupling ក៏ដោយ នៅតែមានន័យថា `node` នឹងរំពឹងថាអ្វីមួយនៅក្នុងបរិស្ថានរបស់វាគឺជាការពិត។ ទស្សនវិជ្ជានៃការរចនាគម្រោងគួរតែការពារកុំឱ្យរឿងនេះកើតឡើង។ ប្រសិនបើមិនដូច្នេះទេ ការទទួលខុសត្រូវជាប់ពីកំណើតនៃកូដនឹងបង្ខំអ្នកអភិវឌ្ឍន៍ឱ្យប្រើឯកសារ (documentation) ដើម្បីតាមដានទំនាក់ទំនងវត្ថុនៅកម្រិតមីក្រូស្កុប; នេះត្រូវបានគេស្គាល់ថាជាអភិវឌ្ឍន៍នរក (development hell)។ ការសរសេរកូដដែលពឹងផ្អែកលើឯកសារខាងក្រៅដើម្បីប្រើប្រាស់វាដោយសុវត្ថិភាព គឺងាយនឹងមានកំហុសតាមលំនាំដើម។

ដើម្បីជៀសវាងការបង្កើត និងថែរក្សាឯកសារបែបនេះ អ្នកបំលែង `node` ដែលពឹងផ្អែក ("child" ខាងលើ) ទៅជាស្គ្រីបឧបករណ៍ (tool script) ដែលអនុវត្ត `_get_configuration_warnings()`។ ការត្រឡប់ `PackedStringArray` ដែលមិនទទេពីវានឹងធ្វើឱ្យចំណុច `Scene dock` បង្កើតរូបតំណាងការព្រមានមួយជាមួយនឹងខ្សែអក្សរជាចំណងជើងឧបករណ៍ (tooltip) នៅក្បែរ `node`។ នេះគឺជារូបតំណាងដូចគ្នាដែលលេចឡើងសម្រាប់ `nodes` ដូចជា [Area2D](https://docs.godotengine.org/en/stable/classes/class_area2d.html#class-area2d) នៅពេលដែលវាគ្មានកូន [CollisionShape2D](https://docs.godotengine.org/en/stable/classes/class_collisionshape2d.html#class-collisionshape2d) `nodes` ត្រូវបានកំណត់។ កម្មវិធីនិពន្ធ (editor) បន្ទាប់មកធ្វើឯកសារដោយខ្លួនឯង (self-documents) សម្រាប់ឆាកតាមរយៈកូដស្គ្រីប។ មិនចាំបាច់មានការចម្លងខ្លឹមសារតាមរយៈឯកសារនោះទេ។

ចំណុចប្រទាក់អ្នកប្រើ (GUI) បែបនេះអាចជូនដំណឹងកាន់តែប្រសើរដល់អ្នកប្រើប្រាស់គម្រោងអំពីព័ត៌មានសំខាន់ៗអំពី `Node`។ តើវាមានការពឹងផ្អែកខាងក្រៅដែរឬទេ? តើការពឹងផ្អែកទាំងនោះត្រូវបានបំពេញហើយឬនៅ? អ្នកសរសេរកម្មវិធីផ្សេងទៀត ហើយជាពិសេសអ្នករចនា និងអ្នកសរសេរ នឹងត្រូវការការណែនាំច្បាស់លាស់នៅក្នុងសារដែលប្រាប់ពួកគេថាត្រូវធ្វើអ្វីដើម្បីកំណត់រចនាសម្ព័ន្ធវា។

ដូច្នេះ ហេតុអ្វីបានជាការប្តូរដ៏ស្មុគស្មាញទាំងអស់នេះដំណើរការ? អី្វក៏ព្រោះថាឆាកដំណើរការបានល្អបំផុតនៅពេលដែលពួកវាដំណើរការតែម្នាក់ឯង។ ប្រសិនបើមិនអាចដំណើរការតែម្នាក់ឯងបាន ការធ្វើការជាមួយអ្នកដទៃដោយមិនបញ្ចេញឈ្មោះ (ជាមួយនឹងការពឹងផ្អែករឹងមាំតិចតួច ឧ. loose coupling) គឺជាជម្រើសល្អបំផុតបន្ទាប់។ ជាធម្មតា ការផ្លាស់ប្តូរអាចនឹងត្រូវធ្វើឡើងចំពោះ `class` មួយ ហើយប្រសិនបើការផ្លាស់ប្តូរទាំងនេះបណ្តាលឱ្យវាធ្វើអន្តរកម្មជាមួយឆាកផ្សេងទៀតតាមរបៀបដែលមិនបានរំពឹងទុក នោះអ្វីៗនឹងចាប់ផ្តើមបែកខ្ញែក។ ចំណុចសំខាន់នៃការប្រយោលទាំងអស់នេះគឺដើម្បីជៀសវាងការបញ្ចប់នៅក្នុងស្ថានភាពដែលការផ្លាស់ប្តូរ `class` មួយបណ្តាលឱ្យប៉ះពាល់អវិជ្ជមានដល់ `classes` ផ្សេងទៀតដែលពឹងផ្អែកលើវា។

ស្គ្រីប និងឆាក ជាផ្នែកពង្រីកនៃ `classes` របស់ម៉ាស៊ីន គួរតែអនុវត្តតាមគោលការណ៍ `OOP` _ទាំងអស់_។ ឧទាហរណ៍រួមមាន...

## ការជ្រើសរើសរចនាសម្ព័ន្ធដើមឈើ `node`[](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html#choosing-a-node-tree-structure)

អ្នកអាចនឹងចាប់ផ្តើមធ្វើការលើហ្គេមមួយ ប៉ុន្តែត្រូវបានគេធ្វើឱ្យភ័យស្លន់ស្លោដោយលទ្ធភាពដ៏ធំធេងនៅចំពោះមុខអ្នក។ អ្នកអាចដឹងថាអ្នកចង់ធ្វើអ្វី ប្រព័ន្ធអ្វីដែលអ្នកចង់មាន ប៉ុន្តែ _នៅឯណា_ ដែលអ្នកដាក់ពួកវាទាំងអស់? របៀបដែលអ្នកធ្វើហ្គេមរបស់អ្នកតែងតែអាស្រ័យលើអ្នក។ អ្នកអាចបង្កើតដើមឈើ `node` តាមវិធីរាប់មិនអស់។ ប្រសិនបើអ្នកមិនច្បាស់ ការណែនាំនេះអាចផ្តល់ឱ្យអ្នកនូវគំរូនៃរចនាសម្ព័ន្ធល្អមួយដើម្បីចាប់ផ្តើម។

ហ្គេមមួយគួរតែតែងតែមាន "ចំណុចចាប់ផ្តើម" (entry point); កន្លែងណាមួយដែលអ្នកអាចតាមដានបានយ៉ាងច្បាស់ថាតើអ្វីៗចាប់ផ្តើមនៅឯណា ដើម្បីឱ្យអ្នកអាចតាមដានលោជីខ្វល់ (logic) នៅពេលដែលវាបន្តទៅកន្លែងផ្សេង។ វាក៏ដើរតួយ៉ាងជាទិដ្ឋភាពពីលើអាកាស (bird's eye view) នៃទិន្នន័យ និងលោជីខ្វល់ផ្សេងទៀតទាំងអស់នៅក្នុងកម្មវិធីផងដែរ។ សម្រាប់កម្មវិធីបែបប្រពៃណី នេះជាធម្មតាគឺជា `function` "main"។ នៅក្នុង Godot វាគឺជា `Main node`។

> * Node "Main" (main.gd)

ស្គ្រីប `main.gd` នឹងដើរតួយ៉ាងជាអ្នកត្រួតពិនិត្យចម្បងនៃហ្គេមរបស់អ្នក។

បន្ទាប់មកអ្នកមាន "ពិភពលោក" (World) ក្នុងហ្គេម (មួយជា 2D ឬ 3D)។ នេះអាចជាកូនរបស់ `Main`។ បន្ថែមពីលើនេះ អ្នកនឹងត្រូវការ `GUI` ចម្បងសម្រាប់ហ្គេមរបស់អ្នកដែលគ្រប់គ្រងម៉ឺនុយ និងវីដហ្គេត (widgets) ផ្សេងៗដែលគម្រោងត្រូវការ។

> * Node "Main" (main.gd)
>   * Node2D/Node3D "World" (game\_world.gd)
>   * Control "GUI" (gui.gd)

នៅពេលផ្លាស់ប្តូរកម្រិត (levels) អ្នកអាចប្តូរកូនៗរបស់ `node` "World"។ [ការផ្លាស់ប្តូរឆាកដោយដៃ](https://docs.godotengine.org/en/stable/tutorials/scripting/change_scenes_manually.html#doc-change-scenes-manually) ផ្តល់ឱ្យអ្នកនូវការគ្រប់គ្រងពេញលេញលើរបៀបដែលពិភពលោកហ្គេមរបស់អ្នកផ្លាស់ប្តូរ។

ជំហានបន្ទាប់គឺពិចារណាថាតើប្រព័ន្ធលេងហ្គេម (gameplay systems) អ្វីខ្លះដែលគម្រោងរបស់អ្នកត្រូវការ។ ប្រសិនបើអ្នកមានប្រព័ន្ធមួយដែល...

1. តាមដានទិន្នន័យទាំងអស់របស់វានៅខាងក្នុង
2. គួរតែអាចចូលប្រើបានជាសកល (globally accessible)
3. គួរតែមាននៅក្នុងភាពឯកោ (exist in isolation)

... នោះអ្នកគួរតែបង្កើត [autoload 'singleton' node](https://docs.godotengine.org/en/stable/tutorials/scripting/singletons_autoload.html#doc-singletons-autoload)។

> **ចំណាំ** សម្រាប់ហ្គេមតូចៗ ជម្រើសដ៏សាមញ្ញមួយដែលមានការគ្រប់គ្រងតិចជាងនេះ គឺការមាន "Game" singleton ដែលគ្រាន់តែហៅ [SceneTree.change\_scene\_to\_file()](https://docs.godotengine.org/en/stable/classes/class_scenetree.html#class-scenetree-method-change-scene-to-file) `method` ដើម្បីប្តូរខ្លឹមសាររបស់ឆាកចម្បង។ រចនាសម្ព័ន្ធនេះទ្រទ្រង់ "World" ជា `node` ហ្គេមចម្បងស្ទើរតែទាំងស្រុង។

`GUI` ណាមួយក៏ត្រូវតែជា `singleton` ផ្នែកបណ្តោះអាសន្ននៃ "World" ឬត្រូវបានបន្ថែមដោយដៃជាកូនផ្ទាល់របស់ឫស (root)។ បើមិនដូច្នេះទេ `GUI nodes` ក៏នឹងលុបខ្លួនឯងចោលក្នុងអំឡុងពេលផ្លាស់ប្តូរឆាកផងដែរ។

ប្រសិនបើអ្នកមានប្រព័ន្ធដែលកែប្រែទិន្នន័យរបស់ប្រព័ន្ធផ្សេងទៀត អ្នកគួរតែកំណត់ពួកវាជាស្គ្រីប ឬឆាកផ្ទាល់ខ្លួនរបស់ពួកវា ជាជាង `autoloads`។ សម្រាប់ព័ត៌មានបន្ថែម សូមមើល [Autoloads versus regular nodes](https://docs.godotengine.org/en/stable/tutorials/best_practices/autoloads_versus_regular_nodes.html#doc-autoloads-versus-regular-nodes)។

ប្រព័ន្ធរង (subsystem) នីមួយៗនៅក្នុងហ្គេមរបស់អ្នកគួរតែមានផ្នែកផ្ទាល់ខ្លួននៅក្នុង `SceneTree`។ អ្នកគួរប្រើទំនាក់ទំនងមេ-កូនតែនៅក្នុងករណីដែល `nodes` គឺជាធាតុផ្សំមានប្រសិទ្ធភាពរបស់មេរបស់ពួកវាប៉ុណ្ណោះ។ តើការយកមេចេញមានន័យសមហេតុផលថាកូនៗគួរតែត្រូវបានយកចេញផងដែរឬទេ? ប្រសិនបើមិនមែនទេ នោះវាគួរតែមានកន្លែងផ្ទាល់ខ្លួននៅក្នុងលំដាប់ថ្នាក់ជាកូនបង្កើត (sibling) ឬទំនាក់ទំនងផ្សេងទៀត។

> **ចំណាំ** នៅក្នុងករណីខ្លះ អ្នកត្រូវការ `nodes` ដែលបានបំបែកទាំងនេះ _ផងដែរ_ ដើម្បីដាក់ទីតាំងរបស់ពួកវាធៀបនឹងគ្នាទៅវិញទៅមក។ អ្នកអាចប្រើ [RemoteTransform](https://docs.godotengine.org/en/stable/classes/class_remotetransform3d.html#class-remotetransform3d) / [RemoteTransform2D](https://docs.godotengine.org/en/stable/classes/class_remotetransform2d.html#class-remotetransform2d) `nodes` សម្រាប់គោលបំណងនេះ។ ពួកវានឹងអនុញ្ញាតឱ្យ `node` គោលដៅតំណពូជដោយមានលក្ខខណ្ឌនូវធាតុបំលែង (transform elements) ដែលបានជ្រើសរើសពី `Remote* node`។ ដើម្បីកំណត់ `target` [NodePath](https://docs.godotengine.org/en/stable/classes/class_nodepath.html#class-nodepath) សូមប្រើមួយក្នុងចំណោមខាងក្រោម៖
>
> 1. ភាគីទីបីដែលអាចទុកចិត្តបាន ទំនងជា `node` មេ ដើម្បីធ្វើជាអ្នកសម្របសម្រួលការកំណត់។
> 2. ក្រុម (group) ដើម្បីទាញយកការយោងទៅ `node` ដែលចង់បាន (ដោយសន្មតថានឹងមានតែមួយគត់នៃគោលដៅ)។

ពេលណាដែលអ្នកគួរធ្វើបែបនេះគឺអាស្រ័យលើអត្តន័យ។ ភាពស្មុគស្មាញកើតឡើងនៅពេលដែលអ្នកត្រូវគ្រប់គ្រងលម្អិត (micro-manage) ពេលណាដែល `node` មួយត្រូវផ្លាស់ទីជុំវិញ `SceneTree` ដើម្បីរក្សាខ្លួនឯង។ ឧទាហរណ៍...

* បន្ថែម `node` "player" ទៅ "room"។
* ត្រូវការផ្លាស់ប្តូរបន្ទប់ ដូច្នេះអ្នកត្រូវលុបបន្ទប់បច្ចុប្បន្ន។
*   មុនពេលបន្ទប់អាចត្រូវបានលុប អ្នកត្រូវរក្សាទុក និង/ឬផ្លាស់ទីអ្នកលេង (player)។

    ប្រសិនបើអង្គចងចាំ (memory) មិនមែនជាកង្វល់ អ្នកអាច...

    * បង្កើតបន្ទប់ថ្មី។
    * ផ្លាស់ទីអ្នកលេងទៅបន្ទប់ថ្មី។
    * លុបបន្ទប់ចាស់។

    ប្រសិនបើអង្គចងចាំគឺជាកង្វល់ ផ្ទុយទៅវិញ អ្នកនឹងត្រូវ...

    * ផ្លាស់ទីអ្នកលេងទៅកន្លែងផ្សេងទៀតនៅក្នុងដើមឈើ។
    * លុបបន្ទប់។
    * បង្កើតឧទាហរណ៍ (Instantiate) និងបន្ថែមបន្ទប់ថ្មី។
    * បន្ថែមអ្នកលេងឡើងវិញទៅបន្ទប់ថ្មី។

បញ្ហានោះគឺថាអ្នកលេងនៅទីនេះគឺជា "ករណីពិសេស" ដែលអ្នកអភិវឌ្ឍន៍ត្រូវ _ដឹង_ ថាពួកគេត្រូវដោះស្រាយអ្នកលេងតាមរបៀបនេះសម្រាប់គម្រោង។ វិធីតែមួយគត់ដើម្បីចែករំលែកព័ត៌មាននេះដោយអាចទុកចិត្តបានជាក្រុមគឺ _ធ្វើឯកសារ_ (document) វា។ ការរក្សាព័ត៌មានលម្អិតនៃការអនុវត្តនៅក្នុងឯកសារគឺគ្រោះថ្នាក់។ វាគឺជាបន្ទុកក្នុងការថែរក្សា ធ្វើឱ្យតានតឹងដល់ការអានកូដ និងធ្វើឱ្យខ្លឹមសារបញ្ញា (intellectual content) នៃគម្រោងកើនឡើងដោយមិនចាំបាច់។

នៅក្នុងហ្គេមដែលស្មុគស្មាញជាងមុនដែលមានទ្រព្យសម្បត្តិធំៗ វាអាចជាគំនិតល្អជាងមុនក្នុងការរក្សាអ្នកលេងនៅកន្លែងផ្សេងទៀតនៅក្នុង `SceneTree` ទាំងស្រុង។ នេះនាំឱ្យមាន៖

1. ភាពស៊ីសង្វាក់គ្នាកាន់តែច្រើន។
2. គ្មាន "ករណីពិសេស" ដែលត្រូវធ្វើឯកសារ និងថែរក្សានៅកន្លែងណាមួយ។
3. គ្មានឱកាសសម្រាប់កំហុសកើតឡើងព្រោះព័ត៌មានលម្អិតទាំងនេះមិនត្រូវបានគិតគូរ។

ផ្ទុយទៅវិញ ប្រសិនបើអ្នកធ្លាប់ត្រូវការ `node` កូនដែល _មិន_ តំណពូជការបំលែង (transform) របស់មេរបស់វា អ្នកមានជម្រើសដូចខាងក្រោម៖

1. ដំណោះស្រាយ **បែបប្រកាស** (declarative)៖ ដាក់ [Node](https://docs.godotengine.org/en/stable/classes/class_node.html#class-node) នៅចន្លោះពួកវា។ ដោយសារតែវាមិនមានការបំលែង (transform) ទេ ពួកវានឹងមិនបញ្ជូនព័ត៌មាននេះទៅកូនៗរបស់វាទេ។
2. ដំណោះស្រាយ **បែបបញ្ជា** (imperative)៖ ប្រើលក្ខណៈសម្បត្តិ `top_level` សម្រាប់ [CanvasItem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html#class-canvasitem-property-top-level) ឬ [Node3D](https://docs.godotengine.org/en/stable/classes/class_node3d.html#class-node3d-property-top-level) `node`។ នេះនឹងធ្វើឱ្យ `node` មិនអើពើនឹងការបំលែងដែលបានតំណពូជរបស់វា។

> **ចំណាំ** ប្រសិនបើកំពុងបង្កើតហ្គេមបណ្តាញ (networked game) សូមចងចាំថាតើ `nodes` និងប្រព័ន្ធលេងហ្គេម (gameplay systems) ណាខ្លះដែលពាក់ព័ន្ធនឹងអ្នកលេងទាំងអស់ ធៀបនឹងអ្នកដែលពាក់ព័ន្ធតែជាមួយសេវាកម្មផ្តល់អាជ្ញាប័ណ្ណ (authoritative server)។ ឧទាហរណ៍ អ្នកប្រើប្រាស់មិនចាំបាច់មានច្បាប់ចម្លងនៃលោជីខ្វល់ "PlayerController" របស់អ្នកលេងទាំងអស់នោះទេ - ពួកគេគ្រាន់តែត្រូវការរបស់ពួកគេផ្ទាល់ប៉ុណ្ណោះ។ ការរក្សាពួកវានៅក្នុងមែកធាងដាច់ដោយឡែកពី "world" អាចជួយសម្រួលដល់ការគ្រប់គ្រងការតភ្ជាប់ហ្គេម និងអ្វីៗបែបនេះ។

គន្លឹះនៃការរៀបចំឆាកគឺពិចារណា `SceneTree` ជាលក្ខខណ្ឌទំនាក់ទំនង (relational terms) ជាជាងលក្ខខណ្ឌទីតាំង (spatial terms)។ តើ `nodes` ពឹងផ្អែកលើអត្ថិភាពរបស់មេរបស់ពួកវាដែរឬទេ? ប្រសិនបើមិនមែនទេ នោះពួកវាអាចរីកចម្រើនដោយខ្លួនឯងនៅកន្លែងផ្សេង។ ប្រសិនបើពួកវាពឹងផ្អែក នោះវាសមហេតុផលដែលពួកវាគួរតែជាកូនរបស់មេនោះ (ហើយទំនងជាផ្នែកមួយនៃឆាករបស់មេនោះ ប្រសិនបើពួកវាមិនទាន់មាន)។

តើនេះមានន័យថា `nodes` ខ្លួនឯងគឺជាសមាសធាតុ (components) មែនទេ? មិនមែនទាល់តែសោះ។ ដើមឈើ `node` របស់ Godot បង្កើតទំនាក់ទំនងប្រមូលផ្តុំ (aggregation relationship) មិនមែនជាការផ្សំ (composition) នោះទេ។ ប៉ុន្តែខណៈដែលអ្នកនៅតែមានភាពបត់បែនក្នុងការផ្លាស់ទី `nodes` ជុំវិញ វានៅតែល្អបំផុតនៅពេលដែលការផ្លាស់ទីបែបនេះមិនចាំបាច់តាមលំនាំដើម។
