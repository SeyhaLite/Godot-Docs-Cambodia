
# 6.តើពេលណា និង របៀបជៀសវាងការប្រើប្រាស់ Nodes សម្រាប់អ្វីៗគ្រប់យ៉ាង 

Nodes មានតម្លៃថោកក្នុងការបង្កើត ប៉ុន្តែសូម្បីតែពួកវាក៏មានដែនកំណត់របស់វាដែរ។ គម្រោងមួយអាចមាន Nodes រាប់หมื่น ឬរាប់សែនដែលកំពុងធ្វើការងារផ្សេងៗ។ ទោះជាយ៉ាងណាក៏ដោយ កាន់តែស្មុគស្មាញជាមួយឥរិយាបថរបស់វា កាន់តែបង្កើនភាពតានតឹងដែលវាបន្ថែមទៅលើដំណើរការរបស់គម្រោង។

Godot ផ្តល់នូវវត្ថុដែលមានទម្ងន់ស្រាលជាងសម្រាប់បង្កើត APIs ដែល Nodes ប្រើប្រាស់។ ចូរចងចាំរក្សាទុកនូវជម្រើសទាំងនេះនៅពេលរចនាថាតើអ្នកចង់សាងសង់មុខងាររបស់គម្រោងអ្នកយ៉ាងដូចម្តេច។

1.  [Object](https://docs.godotengine.org/en/stable/classes/class_object.html#class-object): វត្ថុដែលមានទម្ងន់ស្រាលបំផុត, Object ដើមត្រូវតែប្រើការគ្រប់គ្រងអង្គចងចាំដោយដៃ។ ដោយនិយាយដូច្នេះ វាមិនពិបាកពេកទេក្នុងការបង្កើតរចនាសម្ព័ន្ធទិន្នន័យផ្ទាល់ខ្លួនរបស់អ្នក ឬសូម្បីតែរចនាសម្ព័ន្ធ Node ដែលមានទម្ងន់ស្រាលជាង [Node](https://docs.godotengine.org/en/stable/classes/class_node.html#class-node) class។
    
    -   **ឧទាហរណ៍៖** មើល [Tree](https://docs.godotengine.org/en/stable/classes/class_tree.html#class-tree) node។ វាគាំទ្រកម្រិតខ្ពស់នៃការកែតម្រូវសម្រាប់តារាងមាតិកាដែលមានចំនួនជួរដេកនិងជួរឈរតាមអំពើចិត្ត។ ទិន្នន័យដែលវាប្រើដើម្បីបង្កើតការមើលឃើញរបស់វាគឺជាការពិតជាដើមឈើនៃ [TreeItem](https://docs.godotengine.org/en/stable/classes/class_treeitem.html#class-treeitem) Objects។
        
    -   **អត្ថប្រយោជន៍៖** ការសម្រួល API របស់អ្នកទៅជាវត្ថុដែលមានវិសាលភាពតូចជាង ជួយកែលម្អភាពងាយស្រួលប្រើប្រាស់ និងកែលម្អពេលវេលានៃការធ្វើម្តងទៀត។ ជាជាងការធ្វើការជាមួយ Node library ទាំងមូល អ្នកបង្កើតសំណុំខ្លីនៃ Objects ដែល Node មួយអាចបង្កើត និងគ្រប់គ្រង sub-nodes ដែលសមស្រប។
        
    
    > ចំណាំ
    > 
    > អ្នកគួរតែប្រុងប្រយ័ត្ននៅពេលដោះស្រាយជាមួយពួកវា។ អ្នកអាចរក្សាទុក Object មួយទៅក្នុងអថេរ ប៉ុន្តែការយោងទាំងនេះអាចក្លាយជាមិនត្រឹមត្រូវដោយគ្មានការព្រមាន។ ឧទាហរណ៍ ប្រសិនបើអ្នកបង្កើតរបស់ object សម្រេចចិត្តលុបវាចោលភ្លាមៗ នេះនឹងបណ្តាលឱ្យមានស្ថានភាពកំហុសនៅពេលដែលអ្នកចូលប្រើវាបន្ទាប់។
    
2.  [RefCounted](https://docs.godotengine.org/en/stable/classes/class_refcounted.html#class-refcounted): មានភាពស្មុគស្មាញជាង Object បន្តិចបន្តួចប៉ុណ្ណោះ។ ពួកវាតាមដានការយោងទៅលើខ្លួនឯង លុបតែអង្គចងចាំដែលបានផ្ទុកនៅពេលដែលគ្មានការយោងបន្ថែមទៀតទៅលើខ្លួនឯងប៉ុណ្ណោះ។ ទាំងនេះមានប្រយោជន៍នៅក្នុងភាគច្រើននៃករណីដែលអ្នកត្រូវការទិន្នន័យនៅក្នុង class ផ្ទាល់ខ្លួន។
    
    -   **ឧទាហរណ៍៖** មើល [FileAccess](https://docs.godotengine.org/en/stable/classes/class_fileaccess.html#class-fileaccess) object។ វាដំណើរការដូចជា Object ធម្មតា លើកលែងតែអ្នកមិនចាំបាច់លុបវាដោយខ្លួនឯងទេ។
        
    -   **អត្ថប្រយោជន៍៖** ដូចគ្នានឹង Object។
        
3.  [Resource](https://docs.godotengine.org/en/stable/classes/class_resource.html#class-resource): មានភាពស្មុគស្មាញជាង RefCounted បន្តិចបន្តួចប៉ុណ្ណោះ។ ពួកវាមានសមត្ថភាពជាប់ខ្លួនក្នុងការ serialize/deserialize (ឧ. រក្សាទុក និងផ្ទុក) លក្ខណៈសម្បត្តិរបស់វត្ថុរបស់ពួកវាទៅ/ពីឯកសារ resource របស់ Godot។
    
    -   **ឧទាហរណ៍៖** Scripts, PackedScene (សម្រាប់ឯកសារ scene), និងប្រភេទផ្សេងៗទៀតដូចជានីមួយៗនៃ [AudioEffect](https://docs.godotengine.org/en/stable/classes/class_audioeffect.html#class-audioeffect) classes។ នីមួយៗនៃទាំងនេះអាចត្រូវបានរក្សាទុក និងផ្ទុក ដូច្នេះពួកវាពង្រីកពី Resource។
        
    -   **អត្ថប្រយោជន៍៖** មាន [អ្វីៗជាច្រើនបាននិយាយរួចហើយ](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html#doc-resources) អំពីអត្ថប្រយោជន៍របស់ [Resource](https://docs.godotengine.org/en/stable/classes/class_resource.html#class-resource) លើវិធីសាស្ត្រផ្ទុកទិន្នន័យបែបប្រពៃណី។ ក្នុងបរិបទនៃការប្រើប្រាស់ Resources ជាង Nodes ទោះជាយ៉ាងណាក៏ដោយ អត្ថប្រយោជន៍ចម្បងរបស់ពួកវាគឺនៅក្នុងភាពឆបគ្នាជាមួយ Inspector។ ខណៈពេលដែលមានទម្ងន់ស្រាលស្ទើរតែដូច Object/RefCounted ពួកវានៅតែអាចបង្ហាញ និងនាំចេញលក្ខណៈសម្បត្តិនៅក្នុង Inspector។ នេះអនុញ្ញាតឱ្យពួកវាបំពេញគោលបំណងដូចជា sub-Nodes នៅលើផ្នែកដែលអាចប្រើប្រាស់បាន ប៉ុន្តែក៏កែលម្អដំណើរការផងដែរ ប្រសិនបើអ្នកមានគម្រោងនឹងមាន Resources/Nodes ជាច្រើនបែបនេះនៅក្នុង scenes របស់អ្នក។
