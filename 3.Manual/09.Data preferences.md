# 9.ចំណូលចិត្តទិន្នន័យ 

តើអ្នកធ្លាប់ឆ្ងល់ទេថា គួរដោះស្រាយបញ្ហា X ដោយប្រើរចនាសម្ព័ន្ធទិន្នន័យ Y ឬ Z? អត្ថបទនេះនឹងគ្របដណ្តប់លើប្រធានបទផ្សេងៗដែលទាក់ទងនឹងការសម្រេចចិត្តបែបនេះ។

> **ចំណាំ**
> 
> អត្ថបទនេះលើកឡើងពីប្រតិបត្តិការ «\[អ្វីមួយ\]-time»។ ពាក្យពេចន៍នេះមកពី [Big O Notation](https://rob-bell.net/2009/06/a-beginners-guide-to-big-o-notation/) ក្នុងការវិភាគក្បួនដោះស្រាយ។
> 
> សង្ខេបឱ្យខ្លី វាពិពណ៌នាអំពីស្ថានភាពអាក្រក់បំផុតនៃរយៈពេលដំណើរការ។ តាមភាសាសាមញ្ញ៖
> 
> «នៅពេលទំហំដែនបញ្ហាកើនឡើង រយៈពេលដំណើរការនៃក្បួនដោះស្រាយនឹង...»
> 
> -   ពេលថេរ, `O(1)`: «...មិនកើនឡើងទេ។»
>     
> -   ពេលលោការីត, `O(log n)`: «...កើនឡើងក្នុងអត្រាយឺត។»
>     
> -   ពេលលីនេអ៊ែរ, `O(n)`: «...កើនឡើងក្នុងអត្រាដូចគ្នា។»
>     
> -   ជាដើម។
>     

ស្រមៃមើលថា ប្រសិនបើអ្នកត្រូវដំណើរការចំណុចទិន្នន័យ ៣ លានក្នុងមួយហ្វ្រេម។ វានឹងមិនអាចទៅរួចទេក្នុងការបង្កើតមុខងារនោះដោយប្រើក្បួនដោះស្រាយពេលលីនេអ៊ែរ ព្រោះទំហំទិន្នន័យដ៏ច្រើនសន្ធឹកសន្ធាប់នឹងធ្វើឱ្យរយៈពេលដំណើរការវែងជាងពេលវេលាដែលបានកំណត់។ ផ្ទុយទៅវិញ ការប្រើក្បួនដោះស្រាយពេលថេរអាចដំណើរការប្រតិបត្តិការនោះបានដោយគ្មានបញ្ហា។

ជាទូទៅ អ្នកអភិវឌ្ឍន៍ចង់ជៀសវាងការចូលរួមក្នុងប្រតិបត្តិការពេលលីនេអ៊ែរឱ្យបានច្រើនតាមដែលអាចធ្វើទៅបាន។ ប៉ុន្តែ ប្រសិនបើអ្នករក្សាទំហំនៃប្រតិបត្តិការពេលលីនេអ៊ែរឱ្យតូច ហើយប្រសិនបើអ្នកមិនចាំបាច់អនុវត្តប្រតិបត្តិការនោះញឹកញាប់ទេ នោះវាអាចទទួលយកបាន។ ការថ្លឹងថ្លែងតម្រូវការទាំងនេះ និងការជ្រើសរើសក្បួនដោះស្រាយ / រចនាសម្ព័ន្ធទិន្នន័យត្រឹមត្រូវសម្រាប់ការងារ គឺជាផ្នែកមួយដែលធ្វើឱ្យជំនាញរបស់អ្នកសរសេរកម្មវិធីមានតម្លៃ។

## Array ធៀបនឹង Dictionary ធៀបនឹង Object[](https://docs.godotengine.org/en/stable/tutorials/best_practices/data_preferences.html#array-vs-dictionary-vs-object "Link to this heading")

Godot រក្សាទុកអថេរទាំងអស់នៅក្នុង API សរសេរកម្មវិធីក្នុងថ្នាក់ [Variant](https://docs.godotengine.org/en/stable/engine_details/architecture/variant_class.html#doc-variant-class)។ Variants អាចរក្សាទុករចនាសម្ព័ន្ធទិន្នន័យដែលស្របនឹង Variant ដូចជា [Array](https://docs.godotengine.org/en/stable/classes/class_array.html#class-array) និង [Dictionary](https://docs.godotengine.org/en/stable/classes/class_dictionary.html#class-dictionary) ព្រមទាំង [Objects](https://docs.godotengine.org/en/stable/classes/class_object.html#class-object)។

Godot អនុវត្ត Array ជា `Vector<Variant>`។ ម៉ាស៊ីនរក្សាទុកខ្លឹមសារ Array នៅក្នុងផ្នែកមេម៉ូរីដែលជាប់គ្នា ពោលគឺវាស្ថិតនៅក្នុងជួរជាប់គ្នា។

> **ចំណាំ**
> 
> ចំពោះអ្នកដែលមិនស្គាល់ C++, Vector គឺជាឈ្មោះនៃវត្ថុអារេនៅក្នុងបណ្ណាល័យ C++ បែបប្រពៃណី។ វាជាប្រភេទ «templated» មានន័យថាកំណត់ត្រារបស់វាអាចមានតែប្រភេទជាក់លាក់មួយប៉ុណ្ណោះ (បង្ហាញដោយសញ្ញាង្កៀប)។ ដូច្នេះ ឧទាហរណ៍ [PackedStringArray](https://docs.godotengine.org/en/stable/classes/class_packedstringarray.html#class-packedstringarray) នឹងមានលក្ខណៈដូចជា `Vector<String>`។
> 

ការរក្សាទុកក្នុងមេម៉ូរីជាប់គ្នាបញ្ជាក់ពីដំណើរការប្រតិបត្តិការដូចខាងក្រោម៖

-   **Iterate:** លឿនបំផុត។ ល្អសម្រាប់រង្វិលជុំ។
    
    > -   Op: វាគ្រាន់តែបង្កើនរាប់ថ្មីដើម្បីទៅដល់កំណត់ត្រាបន្ទាប់ប៉ុណ្ណោះ។
    >     
    
-   **Insert, Erase, Move:** អាស្រ័យលើទីតាំង។ ជាទូទៅយឺត។
    
    > -   Op: ការបន្ថែម/លុប/ផ្លាស់ទីខ្លឹមសារពាក់ព័ន្ធនឹងការផ្លាស់ទីកំណត់ត្រាដែលនៅជាប់គ្នា (ដើម្បីបង្កើតកន្លែង / បំពេញកន្លែង)។
    >     
    > -   បន្ថែម/លុប *ពីចុង* លឿន។
    >     
    > -   បន្ថែម/លុប *ពីទីតាំងណាមួយ* យឺត។
    >     
    > -   យឺតបំផុតសម្រាប់បន្ថែម/លុប *ពីខាងមុខ*។
    >     
    > -   ប្រសិនបើធ្វើការបញ្ចូល/លុបច្រើន *ពីខាងមុខ* នោះ...
    >     
    >     > 1.  បញ្ច្រាសអារេ។
    >     >     
    >     > 2.  ធ្វើរង្វិលជុំដែលអនុវត្តការផ្លាស់ប្តូរ Array *នៅចុង*។
    >     >     
    >     > 3.  បញ្ច្រាសអារេម្តងទៀត។
    >     >     
    >     
    >     នេះធ្វើឱ្យមានច្បាប់ចម្លងអារេត្រឹមតែ ២ ដងប៉ុណ្ណោះ (នៅតែជាពេលថេរ ប៉ុន្តែយឺត) បើធៀបនឹងការចម្លងប្រហែល ១/២ នៃអារេ ជាមធ្យម, N ដង (ពេលលីនេអ៊ែរ)។
    >     
    
-   **Get, Set:** លឿនបំផុត *តាមទីតាំង*។ ឧ. អាចស្នើសុំកំណត់ត្រាលំដាប់ទី ០, ទី ២, ទី ១០ ជាដើម ប៉ុន្តែមិនអាចបញ្ជាក់ថាតើអ្នកចង់បានកំណត់ត្រាណាទេ។

    >     
    
-   **Find:** យឺតបំផុត។ កំណត់សន្ទស្សន៍/ទីតាំងនៃតម្លៃមួយ។
    
    > -   Op: ត្រូវធ្វើការធ្វើដំណើរតាមអារេ និងប្រៀបធៀបតម្លៃរហូតដល់រកឃើញការផ្គូផ្គង។
    >     
    >     > -   ដំណើរការក៏អាស្រ័យលើថាតើអ្នកត្រូវការការស្វែងរកពេញលេញដែរឬទេ។
    >     >     
    >     
    > -   ប្រសិនបើរក្សាទុកឱ្យមានលំដាប់ ប្រតិបត្តិការស្វែងរកផ្ទាល់ខ្លួនអាចនាំវាទៅរកពេលលោការីត (លឿនបើធៀប)។ អ្នកប្រើប្រាស់ទូទៅនឹងមិនស្រួលចិត្តនឹងរឿងនេះទេ។ ធ្វើឡើងដោយការតម្រៀបអារេឡើងវិញបន្ទាប់ពីការកែសម្រួលនីមួយៗ និងសរសេរក្បួនដោះស្រាយស្វែងរកដែលដឹងពីលំដាប់។
    >     
    

Godot អនុវត្ត Dictionary ជា `HashMap<Variant, Variant, VariantHasher, StringLikeVariantComparator>`។ ម៉ាស៊ីនរក្សាទុកអារេតូចមួយ (ចាប់ផ្តើមដំបូងត្រឹម 2^3 ឬ ៨ កំណត់ត្រា) នៃគូសោ-តម្លៃ។ នៅពេលអ្នកព្យាយាមចូលប្រើតម្លៃមួយ ពួកគេផ្តល់សោមួយឱ្យវា។ បន្ទាប់មកវា *hash* សោនោះ ពោលគឺបំលែងវាទៅជាលេខ។ «hash» ត្រូវបានប្រើដើម្បីគណនាសន្ទស្សន៍ចូលទៅក្នុងអារេ។ ជាអារេ បន្ទាប់មក HM មានការចូលមើលលឿននៅក្នុង «តារាង» នៃសោដែលភ្ជាប់ទៅនឹងតម្លៃ។ នៅពេលដែល HashMap ពេញពេក វាកើនឡើងទៅជាអំណាចបន្ទាប់នៃ ២ (ដូច្នេះ ១៦ កំណត់ត្រា បន្ទាប់មក ៣២ ជាដើម) និងសាងសង់រចនាសម្ព័ន្ធឡើងវិញ។

3.  **ភាពងាយស្រួល:** ប្រសិនបើអ្នកមានរចនាសម្ព័ន្ធទិន្នន័យស្រដៀងគ្នារួចហើយក្នុងចិត្ត នោះការពង្រីកពីថ្នាក់ដែលមានស្រាប់ធ្វើឱ្យភារកិច្ចក្នុងការសាងសង់រចនាសម្ព័ន្ធទិន្នន័យកាន់តែងាយស្រួល។ ផ្ទុយទៅវិញ Arrays និង Dictionaries មិនបំពេញរាល់ករណីប្រើប្រាស់ដែលអ្នកអាចមានទេ។
    

Objects ក៏ផ្តល់ឱកាសដល់អ្នកប្រើប្រាស់ក្នុងការបង្កើតរចនាសម្ព័ន្ធទិន្នន័យដែលមានឯកទេសខ្ពស់ជាងនេះទៀត។ ជាមួយវា អ្នកអាចរចនា List, Binary Search Tree, Heap, Splay Tree, Graph, Disjoint Set និងជម្រើសផ្សេងៗទៀតជាច្រើនរបស់អ្នកផ្ទាល់។

«ហេតុអ្វីបានជាមិនប្រើ Node សម្រាប់រចនាសម្ព័ន្ធដើមឈើ?» អ្នកអាចសួរ។ អីចឹង ថ្នាក់ Node មានអ្វីៗដែលនឹងមិនពាក់ព័ន្ធនឹងរចនាសម្ព័ន្ធទិន្នន័យផ្ទាល់ខ្លួនរបស់អ្នកទេ។ ដូច្នេះ វាអាចមានប្រយោជន៍ក្នុងការសាងសង់ប្រភេទ node ផ្ទាល់ខ្លួនរបស់អ្នកនៅពេលសាងសង់រចនាសម្ព័ន្ធដើមឈើ។

```gdscript
class_name TreeNode
extends Object

var _parent: TreeNode = null
var _children := []

func _notification(p_what):
	match p_what:
		NOTIFICATION_PREDELETE:
			# Destructor.
			for a_child in _children:
				a_child.free()
```

ពីទីនេះ អ្នកអាចបង្កើតរចនាសម្ព័ន្ធផ្ទាល់ខ្លួនរបស់អ្នកជាមួយនឹងមុខងារជាក់លាក់ ដែលកំណត់ដោយការស្រមើលស្រមៃរបស់អ្នកប៉ុណ្ណោះ។

## ការរាប់: int ធៀបនឹង string[](https://docs.godotengine.org/en/stable/tutorials/best_practices/data_preferences.html#enumerations-int-vs-string "Link to this heading")

ភាសាភាគច្រើនផ្តល់ជម្រើសប្រភេទ enumeration។ GDScript ក៏មិនខុសគ្នាដែរ ប៉ុន្តែផ្ទុយពីភាសាភាគច្រើនផ្សេងទៀត វាអនុញ្ញាតឱ្យអ្នកប្រើលេខគត់ ឬខ្សែអក្សរសម្រាប់តម្លៃ enum (ចុងក្រោយនៅពេលប្រើ annotation `@export_enum` ក្នុង GDScript)។ សំណួរក៏កើតឡើង «តើគួរប្រើមួយណា?»

ចម្លើយខ្លីគឺ «អ្វីដែលអ្នកស្រួលចិត្តជាងមុន។» នេះគឺជាមុខងារជាក់លាក់សម្រាប់ GDScript ហើយមិនមែនសម្រាប់ការសរសេរកម្មវិធី Godot ជាទូទៅទេ; ភាសាផ្តល់អាទិភាពលើភាពងាយស្រួលប្រើជាងប្រសិទ្ធភាព។

នៅកម្រិតបច្ចេកទេស ការប្រៀបធៀបលេខគត់ (ពេលថេរ) នឹងកើតឡើងលឿនជាងការប្រៀបធៀបខ្សែអក្សរ (ពេលលីនេអ៊ែរ)។ ប្រសិនបើអ្នកចង់រក្សាទម្លាប់ភាសាផ្សេងទៀតទោះយ៉ាងណា នោះអ្នកគួរប្រើលេខគត់។

បញ្ហាចម្បងជាមួយការប្រើលេខគត់កើតឡើងនៅពេលដែលអ្នកចង់ *បោះពុម្ព* តម្លៃ enum មួយ។ ជាលេខគត់ ការព្យាយាមបោះពុម្ព `MY_ENUM` នឹងបោះពុម្ព `៥` ឬអ្វីមួយបែបនេះ ជាជាងអ្វីមួយដូចជា `"MyEnum"`។ ដើម្បីបោះពុម្ព enum លេខគត់ អ្នកនឹងត្រូវសរសេរ Dictionary ដែលផ្គូផ្គងតម្លៃខ្សែអក្សរដែលត្រូវគ្នាសម្រាប់ enum នីមួយៗ។

ប្រសិនបើគោលបំណងចម្បងនៃការប្រើ enum គឺសម្រាប់ការបោះពុម្ពតម្លៃ ហើយអ្នកចង់ដាក់ពួកគេជាមួយគ្នាជាគំនិតដែលទាក់ទងគ្នា នោះវាមានន័យក្នុងការប្រើពួកគេជាខ្សែអក្សរ។ តាមរបៀបនេះ រចនាសម្ព័ន្ធទិន្នន័យដាច់ដោយឡែកមួយដើម្បីអនុវត្តលើការបោះពុម្ពគឺមិនចាំបាច់ទេ។

## AnimatedTexture ធៀបនឹង AnimatedSprite2D ធៀបនឹង AnimationPlayer ធៀបនឹង AnimationTree[](https://docs.godotengine.org/en/stable/tutorials/best_practices/data_preferences.html#animatedtexture-vs-animatedsprite2d-vs-animationplayer-vs-animationtree "Link to this heading")

ក្រោមលក្ខខណ្ឌណាដែលអ្នកគួរប្រើថ្នាក់ចលនានីមួយៗរបស់ Godot? ចម្លើយអាចមិនច្បាស់លាស់ភ្លាមៗសម្រាប់អ្នកប្រើ Godot ថ្មីៗទេ។

[AnimatedTexture](https://docs.godotengine.org/en/stable/classes/class_animatedtexture.html#class-animatedtexture) គឺជា texture ដែលម៉ាស៊ីនគូរជាចលនារង្វិលជុំ ជាជាងរូបភាពស្ងៀម។ អ្នកប្រើប្រាស់អាចកែប្រែ...

1.  អត្រាដែលវាផ្លាស់ទីកាត់ផ្នែកនីមួយៗនៃ texture (FPS)។
    
2.  ចំនួនតំបន់ដែលមាននៅក្នុង texture (ហ្វ្រេម)។
    

[RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver) របស់ Godot បន្ទាប់មកគូរតំបន់ទាំងនោះតាមលំដាប់លំដោយក្នុងអត្រាដែលបានកំណត់។ ដំណឹងល្អគឺថានេះមិនពាក់ព័ន្ធនឹងលោជីខលបន្ថែមពីផ្នែកម៉ាស៊ីនទេ។ ដំណឹងអាក្រក់គឺថាអ្នកប្រើប្រាស់មានការត្រួតពិនិត្យតិចតួចណាស់។

ចំណាំផងដែរថា AnimatedTexture គឺជា [Resource](https://docs.godotengine.org/en/stable/classes/class_resource.html#class-resource) ផ្ទុយពីវត្ថុ [Node](https://docs.godotengine.org/en/stable/classes/class_node.html#class-node) ផ្សេងទៀតដែលបានពិភាក្សានៅទីនេះ។ អ្នកអាចបង្កើត [Sprite2D](https://docs.godotengine.org/en/stable/classes/class_sprite2d.html#class-sprite2d) node ដែលប្រើ AnimatedTexture ជា texture របស់វា។ ឬ (អ្វីដែលផ្សេងទៀតមិនអាចធ្វើបាន) អ្នកអាចបន្ថែម AnimatedTextures ជា tiles ក្នុង [TileSet](https://docs.godotengine.org/en/stable/classes/class_tileset.html#class-tileset) និងបញ្ចូលវាជាមួយ [TileMapLayer](https://docs.godotengine.org/en/stable/classes/class_tilemaplayer.html#class-tilemaplayer) សម្រាប់ផ្ទៃខាងក្រោយដែលមានចលនាស្វ័យប្រវត្តិជាច្រើនដែលទាំងអស់បង្ហាញក្នុងការហៅគូរតែមួយដែលបានដាក់ជាក្រុម។

[AnimatedSprite2D](https://docs.godotengine.org/en/stable/classes/class_animatedsprite2d.html#class-animatedsprite2d) node រួមជាមួយធនធាន [SpriteFrames](https://docs.godotengine.org/en/stable/classes/class_spriteframes.html#class-spriteframes) អនុញ្ញាតឱ្យអ្នកបង្កើតលំដាប់ចលនាផ្សេងៗតាមរយៈ spritesheets, ប្តូររវាងចលនា និងត្រួតពិនិត្យល្បឿន ការផ្លាស់ទីតំបន់ និងទិសដៅរបស់ពួកគេ។ នេះធ្វើឱ្យពួកគេសមស្របយ៉ាងល្អសម្រាប់ការត្រួតពិនិត្យចលនាផ្អែកលើហ្វ្រេម 2D។

ប្រសិនបើអ្នកត្រូវការបញ្ឆេះឥទ្ធិពលផ្សេងទៀតទាក់ទងនឹងការផ្លាស់ប្តូរចលនា (ឧទាហរណ៍ បង្កើតឥទ្ធិពលភាគល្អិត ហៅមុខងារ ឬកែប្រែធាតុបរិយាកាសផ្សេងទៀតក្រៅពីចលនាផ្អែកលើហ្វ្រេម) នោះអ្នកនឹងត្រូវប្រើ [AnimationPlayer](https://docs.godotengine.org/en/stable/classes/class_animationplayer.html#class-animationplayer) node រួមជាមួយ AnimatedSprite2D។

AnimationPlayers ក៏ជាឧបករណ៍ដែលអ្នកនឹងត្រូវប្រើផងដែរ ប្រសិនបើអ្នកចង់រចនាប្រព័ន្ធចលនា 2D ដែលស្មុគស្មាញជាងមុន ដូចជា...

1.  **ចលនា Cut-out:** កែប្រែ transforms របស់ sprites នៅពេលដំណើរការ។
    
2.  **ចលនា 2D Mesh:** កំណត់តំបន់សម្រាប់ texture របស់ sprite និងភ្ជាប់ឆ្អឹងខ្នងទៅវា។ បន្ទាប់មកអ្នកធ្វើចលនាលើឆ្អឹងដែលលាតសន្ធឹង និងពត់កោង texture សមាមាត្រទៅនឹងទំនាក់ទំនងរបស់ឆ្អឹងទៅនឹងគ្នាទៅវិញទៅមក។
    
3.  ការលាយបញ្ចូលគ្នានៃខាងលើ។
    

ខណៈដែលអ្នកត្រូវការ AnimationPlayer ដើម្បីរចនាលំដាប់ចលនានីមួយៗសម្រាប់ហ្គេម វាក៏អាចមានប្រយោជន៍ផងដែរក្នុងការបញ្ចូលចលនាសម្រាប់ការលាយ ពោលគឺអនុញ្ញាតឱ្យមានការផ្លាស់ប្តូររលូនរវាងចលនាទាំងនេះ។ ក៏អាចមានរចនាសម្ព័ន្ធថ្នាក់រវាងចលនាដែលអ្នកគ្រោងនឹងធ្វើសម្រាប់វត្ថុរបស់អ្នក។ ទាំងនេះគឺជាករណីដែល [AnimationTree](https://docs.godotengine.org/en/stable/classes/class_animationtree.html#class-animationtree) បង្ហាញភាពលេចធ្លោ។ អ្នកអាចរកការណែនាំលម្អិតអំពីការប្រើប្រាស់ AnimationTree [នៅទីនេះ](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html#doc-animation-tree)។
