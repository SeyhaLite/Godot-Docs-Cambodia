# 5.Autoloads ធៀបនឹង nodes ធម្មតា 

Godot ផ្តល់នូវមុខងារមួយដើម្បីផ្ទុក nodes ដោយស្វ័យប្រវត្តិនៅឫសគល់នៃគម្រោងរបស់អ្នក ដែលអនុញ្ញាតឱ្យអ្នកចូលប្រើវាបានជាសកល ដែលអាចបំពេញតួនាទីជា Singleton: [Singletons (Autoload)](https://docs.godotengine.org/en/stable/tutorials/scripting/singletons_autoload.html#doc-singletons-autoload)។ Nodes ដែលបានផ្ទុកដោយស្វ័យប្រវត្តិទាំងនេះនឹងមិនត្រូវបានលុបចោល (freed) នៅពេលអ្នកផ្លាស់ប្តូរ scene ពីកូដដោយប្រើ [SceneTree.change_scene_to_file](https://docs.godotengine.org/en/stable/classes/class_scenetree.html#class-scenetree-method-change-scene-to-file) ឡើយ។

នៅក្នុងការណែនាំនេះ អ្នកនឹងរៀនពីពេលណាដែលគួរប្រើមុខងារ Autoload និងបច្ចេកទេសដែលអ្នកអាចប្រើដើម្បីជៀសវាងវា។

## បញ្ហាសំឡេងអូឌីយ៉ូដែលកាត់ផ្តាច់[](https://docs.godotengine.org/en/stable/tutorials/best_practices/autoloads_versus_regular_nodes.html#the-cutting-audio-issue "Link to this heading")

ម៉ាស៊ីន (engines) ផ្សេងៗទៀតអាចលើកទឹកចិត្តឱ្យប្រើការបង្កើតថ្នាក់គ្រប់គ្រង (manager classes) ឬ singletons ដែលរៀបចំមុខងារជាច្រើនទៅក្នុងវត្ថុដែលអាចចូលប្រើបានជាសកល។ Godot ផ្តល់នូវវិធីជាច្រើនដើម្បីជៀសវាងស្ថានភាពសកល (global state) ដោយសារតែដើមឈើ node និងសញ្ញា (signals)។

ឧទាហរណ៍ ចូរនិយាយថាយើងកំពុងសាងសង់ហ្គេមបែប platformer ហើយចង់ប្រមូលកាក់ដែលលេងសំឡេងបែបអ៊ីផេក (sound effect)។ មាន node មួយសម្រាប់រឿងនោះ: គឺ [AudioStreamPlayer](https://docs.godotengine.org/en/stable/classes/class_audiostreamplayer.html#class-audiostreamplayer)។ ប៉ុន្តែប្រសិនបើយើងហៅ `AudioStreamPlayer` ខណៈដែលវាកំពុងលេងសំឡេងរួចហើយ សំឡេងថ្មីនឹងកាត់ផ្តាច់សំឡេងដំបូង។

ដំណោះស្រាយមួយគឺសរសេរកូដថ្នាក់គ្រប់គ្រងសំឡេង (sound manager class) ដែលជាសកល និងផ្ទុកដោយស្វ័យប្រវត្តិ។ វាបង្កើតក្រុម (pool) នៃ `AudioStreamPlayer` nodes ដែលធ្វើការវិលជុំ (cycle) តាមរយៈពេលដែលសំណើសំឡេងអ៊ីផេកថ្មីៗចូលមក។ ឧបមាថាយើងហៅថ្នាក់នោះថា `Sound` អ្នកអាចប្រើវាពីទីកន្លែងណាមួយនៅក្នុងគម្រោងរបស់អ្នកដោយហៅ `Sound.play("coin_pickup.ogg")`។ រឿងនេះដោះស្រាយបញ្ហានៅក្នុងរយៈពេលខ្លី ប៉ុន្តែបង្កបញ្ហាច្រើនជាងនេះទៀត៖

1.  **ស្ថានភាពសកល (Global state)**៖ វត្ថុតែមួយឥឡូវនេះទទួលខុសត្រូវលើទិន្នន័យរបស់វត្ថុទាំងអស់។ ប្រសិនបើថ្នាក់ `Sound` មានកំហុស ឬមិនមាន `AudioStreamPlayer` ដែលអាចប្រើបាន គ្រប់ nodes ទាំងអស់ដែលហៅវាអាចនឹងខូច។
    
2.  **ការចូលប្រើសកល (Global access)**៖ ឥឡូវនេះ វត្ថុណាមួយអាចហៅ `Sound.play(sound_path)` ពីទីកន្លែងណាមួយ ដូច្នេះគ្មានវិធីងាយៗដើម្បីរកប្រភពនៃកំហុស (bug) ទៀតទេ។
    
3.  **ការបែងចែកធនធានសកល (Global resource allocation)**៖ ជាមួយក្រុម (pool) នៃ `AudioStreamPlayer` nodes ដែលត្រូវបានរក្សាទុកតាំងពីដំបូង អ្នកអាចនឹងមានតិចពេក និងជួបបញ្ហាកំហុស ឬច្រើនពេក និងប្រើអង្គចងចាំ (memory) ច្រើនជាងការចាំបាច់។
    

ចំណាំ

អំពីការចូលប្រើសកល (global access) បញ្ហាគឺថាកូដណាមួយនៅទីកន្លែងណាមួយអាចផ្ទេរទិន្នន័យខុសទៅកាន់ `Sound` autoload នៅក្នុងឧទាហរណ៍របស់យើង។ ជាលទ្ធផល ដែនដែលត្រូវស្វែងរកដើម្បីជួសជុលកំហុសនោះគ្របដណ្តប់លើគម្រោងទាំងមូល។

នៅពេលអ្នករក្សាកូដនៅក្នុង scene មានតែស្គ្រីបមួយ ឬពីរប៉ុណ្ណោះដែលអាចពាក់ព័ន្ធនឹងសំឡេងអូឌីយ៉ូ។

ប្រៀបធៀបជាមួយនឹងការដែល scene នីមួយៗរក្សា `AudioStreamPlayer` nodes ច្រើនតាមតម្រូវការនៅក្នុងខ្លួនវាផ្ទាល់ ហើយបញ្ហាទាំងអស់នេះនឹងបាត់ទៅវិញ៖

1.  Scene នីមួយៗគ្រប់គ្រងព័ត៌មានស្ថានភាព (state information) របស់ខ្លួនឯង។ ប្រសិនបើមានបញ្ហាជាមួយទិន្នន័យ វានឹងបង្កបញ្ហាតែនៅក្នុង scene តែមួយនោះប៉ុណ្ណោះ។
    
2.  Scene នីមួយៗចូលប្រើតែ nodes របស់ខ្លួនឯងប៉ុណ្ណោះ។ ឥឡូវនេះ ប្រសិនបើមានកំហុស (bug) វាងាយស្រួលក្នុងការរកឃើញថា node មួយណាដែលជាអ្នកបង្ក។
    
3.  Scene នីមួយៗបែងចែកធនធានចំនួនពិតប្រាកដតាមតម្រូវការរបស់វា។
    

## ការគ្រប់គ្រងមុខងារ ឬទិន្នន័យដែលចែករំលែក[](https://docs.godotengine.org/en/stable/tutorials/best_practices/autoloads_versus_regular_nodes.html#managing-shared-functionality-or-data "Link to this heading")

មូលហេតុមួយទៀតដើម្បីប្រើ Autoload អាចជាថាអ្នកចង់ប្រើប្រាស់វិធីសាស្ត្រ ឬទិន្នន័យដដែលនៅទូទាំង scenes ជាច្រើន។

ក្នុងករណីនៃអនុគមន៍ (functions) អ្នកអាចបង្កើតប្រភេទថ្មីនៃ `Node` ដែលផ្តល់នូវលក្ខណៈពិសេសនោះសម្រាប់ scene តែមួយដោយប្រើពាក្យគន្លឹះ [class_name](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_basics.html#doc-gdscript-basics-class-name) នៅក្នុង GDScript។

នៅពេលនិយាយអំពីទិន្នន័យ អ្នកអាច៖

1.  បង្កើតប្រភេទថ្មីនៃ [Resource](https://docs.godotengine.org/en/stable/classes/class_resource.html#class-resource) ដើម្បីចែករំលែកទិន្នន័យ។
    
2.  រក្សាទុកទិន្នន័យនៅក្នុងវត្ថុមួយដែល node នីមួយៗមានសិទ្ធិចូលប្រើ ឧទាហរណ៍ ដោយប្រើប្រាស់លក្ខណៈសម្បត្តិ `owner` ដើម្បីចូលប្រើ node ឫសគល់ (root node) នៃ scene។
    

## ពេលណាដែលអ្នកគួរប្រើ Autoload[](https://docs.godotengine.org/en/stable/tutorials/best_practices/autoloads_versus_regular_nodes.html#when-you-should-use-an-autoload "Link to this heading")

GDScript គាំទ្រការបង្កើតអនុគមន៍ `static` ដោយប្រើ `static func`។ នៅពេលបញ្ចូលគ្នាជាមួយ `class_name` វាធ្វើឱ្យអាចបង្កើតបណ្ណាល័យនៃអនុគមន៍ជំនួយ (helper functions) ដោយមិនចាំបាច់បង្កើត instance ដើម្បីហៅវា។ ដែនកំណត់នៃអនុគមន៍ static គឺថាវាមិនអាចយោងទៅលើអថេរសមាជិក (member variables) អនុគមន៍ដែលមិនមែន static ឬ `self` បានទេ។

ចាប់តាំងពី Godot 4.1 មក GDScript ក៏គាំទ្រអថេរ `static` ដោយប្រើ `static var` ផងដែរ។ នេះមានន័យថាឥឡូវនេះអ្នកអាចចែករំលែកអថេរនៅទូទាំង instances នៃថ្នាក់មួយ ដោយមិនចាំបាច់បង្កើត autoload ដាច់ដោយឡែកមួយទៀតឡើយ។

ទោះយ៉ាងណាក៏ដោយ nodes ដែលបានផ្ទុកដោយស្វ័យប្រវត្តិ (autoloaded nodes) អាចធ្វើឱ្យកូដរបស់អ្នកកាន់តែសាមញ្ញសម្រាប់ប្រព័ន្ធដែលមានវិសាលភាពធំទូលាយ។ ប្រសិនបើ autoload កំពុងគ្រប់គ្រងព័ត៌មានរបស់ខ្លួនឯង ហើយមិនលុកលុយទិន្នន័យរបស់វត្ថុផ្សេងៗទេ នោះវាគឺជាវិធីដ៏ល្អមួយដើម្បីបង្កើតប្រព័ន្ធដែលដោះស្រាយកិច្ចការដែលមានវិសាលភាពធំ។ ឧទាហរណ៍ ប្រព័ន្ធភារកិច្ច (quest) ឬប្រព័ន្ធសន្ទនា (dialogue system)។

ចំណាំ

Autoload *មិនមែន* ជា singleton ជានិច្ចនោះទេ។ គ្មានអ្វីដែលការពារអ្នកពីការបង្កើតច្បាប់ចម្លង (instantiating copies) នៃ node ដែលបានផ្ទុកដោយស្វ័យប្រវត្តិនោះទេ។ Autoload គ្រាន់តែជាឧបករណ៍មួយដែលធ្វើឱ្យ node មួយផ្ទុកដោយស្វ័យប្រវត្តិជាកូន (child) នៃឫសគល់នៃដើមឈើ scene របស់អ្នក ដោយមិនគិតពីរចនាសម្ព័ន្ធ node នៃហ្គេមរបស់អ្នក ឬ scene ណាដែលអ្នកកំពុងដំណើរការ ឧទាហរណ៍ ដោយចុចគ្រាប់ចុច F6។

ជាលទ្ធផល អ្នកអាចទទួលបាន node ដែលបានផ្ទុកដោយស្វ័យប្រវត្តិ ឧទាហរណ៍ autoload មួយឈ្មោះថា `Sound` ដោយហៅ `get_node("/root/Sound")`។

> **ចំណាំ:** ទំព័រនេះមាន iframe(s) ចំនួន 1 ដែលមកពីប្រភពខុសគ្នា (cross-origin) ដែលមិនអាចចូលប្រើបានដោយសារតែគោលនយោបាយសុវត្ថិភាពរបស់កម្មវិធីរុករក (browser)។ មាតិកាមួយចំនួនអាចនឹងបាត់។ តំណភ្ជាប់ទៅកាន់ iframes ទាំងនេះត្រូវបានរក្សាទុកនៅកន្លែងដែលអាចធ្វើទៅបាន។
