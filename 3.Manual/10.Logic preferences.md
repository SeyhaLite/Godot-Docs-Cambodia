# 10.ចំណូលចិត្តផ្នែកលោជីខ

### ចំណូលចិត្តផ្នែកលោជីខ Logic preferences

តើអ្នកធ្លាប់ឆ្ងល់ទេថា តើគួរដោះស្រាយបញ្ហា X ដោយប្រើយុទ្ធសាស្ត្រ Y ឬ Z? អត្ថបទនេះគ្របដណ្តប់លើប្រធានបទផ្សេងៗដែលទាក់ទងនឹងការសម្រេចចិត្តបែបនេះ។

### ការបន្ថែម nodes និងការផ្លាស់ប្តូរ properties៖ តើអ្វីគួរធ្វើមុន?[](https://docs.godotengine.org/en/stable/tutorials/best_practices/logic_preferences.html#adding-nodes-and-changing-properties-which-first)

នៅពេលដែលអ្នកចាប់ផ្តើមដំណើរការ nodes ពីស្គ្រីបនៅពេលដំណើរការ (runtime) អ្នកប្រហែលជាត្រូវផ្លាស់ប្តូរ properties ដូចជា ឈ្មោះ ឬទីតាំងរបស់ node។ ការសម្រេចចិត្តដ៏ពេញនិយមមួយគឺ តើអ្នកគួរផ្លាស់ប្តូរតម្លៃទាំងនេះនៅពេលណា?

វាជាការអនុវត្តល្អបំផុតក្នុងការផ្លាស់ប្តូរតម្លៃលើ node មុនពេលបន្ថែមវាចូលទៅក្នុង scene tree។ setters មួយចំនួននៃ properties មានកូដដើម្បីធ្វើបច្ចុប្បន្នភាពតម្លៃផ្សេងទៀតដែលត្រូវគ្នា ហើយកូដនោះអាចយឺត! ក្នុងករណីភាគច្រើន កូដនេះមិនមានផលប៉ះពាល់ដល់ដំណើរការហ្គេមរបស់អ្នកទេ ប៉ុន្តែនៅក្នុងករណីប្រើប្រាស់ខ្លាំងៗ ដូចជាការបង្កើតដោយនីតិវិធី (procedural generation) វាអាចធ្វើឱ្យហ្គេមរបស់អ្នកដំណើរការយឺតយ៉ាវ។

ដោយសារហេតុផលទាំងនេះ វាជាការអនុវត្តល្អបំផុតជាទូទៅក្នុងការកំណត់តម្លៃដំបូងរបស់ node មុនពេលបន្ថែមវាចូលទៅក្នុង scene tree។ មានករណីលើកលែងមួយចំនួនដែលតម្លៃ _មិនអាច_ ត្រូវបានកំណត់មុនពេលបន្ថែមចូលទៅក្នុង scene tree ដូចជាការកំណត់ទីតាំងសកល (global position)។

### ការផ្ទុក (Loading) ធៀបនឹងការផ្ទុកជាមុន (Preloading)[](https://docs.godotengine.org/en/stable/tutorials/best_practices/logic_preferences.html#loading-vs-preloading)

នៅក្នុង GDScript មានវិធីសាស្ត្រសកល [preload](https://docs.godotengine.org/en/stable/classes/class_%40gdscript.html#class-gdscript-method-preload)។ វាផ្ទុកធនធាននៅពេលដែលអាចធ្វើទៅបានឆាប់បំផុត ដើម្បីដាក់បន្ទុកការងារ "ផ្ទុក" ទៅខាងមុខ និងជៀសវាងការផ្ទុកធនធាននៅពេលដែលកំពុងស្ថិតនៅកណ្តាលកូដដែលងាយរងផលប៉ះពាល់ពីដំណើរការ។

ផ្ទុយមកវិញ វិធីសាស្ត្រ [load](https://docs.godotengine.org/en/stable/classes/class_%40gdscript.html#class-gdscript-method-load) ផ្ទុកធនធានតែនៅពេលដែលវាទៅដល់សេចក្តីថ្លែងការណ៍ load។ មានន័យថា វានឹងផ្ទុកធនធាននៅកន្លែងដែលអាចបណ្តាលឱ្យមានការយឺតយ៉ាវ នៅពេលដែលវាកើតឡើងនៅកណ្តាលដំណើរការដែលងាយរងផលប៉ះពាល់។ អនុគមន៍ `load()` ក៏ជាឈ្មោះជំនួសសម្រាប់ [ResourceLoader.load(path)](https://docs.godotengine.org/en/stable/classes/class_resourceloader.html#class-resourceloader-method-load) ដែលអាចចូលប្រើបានដោយភាសាស្គ្រីប _ទាំងអស់_។

ដូច្នេះ តើការផ្ទុកជាមុន (preloading) កើតឡើងពេលណាបើធៀបនឹងការផ្ទុក (loading) ហើយតើពេលណាគួរប្រើមួយណា? ចូរយើងមើលឧទាហរណ៍មួយ៖

```gdscript
# my_buildings.gd
extends Node

# Note how constant scripts/scenes have a different naming scheme than
# their property variants.

# This value is a constant, so it spawns when the Script object loads.
# The script is preloading the value. The advantage here is that the editor
# can offer autocompletion since it must be a static path.
const BuildingScn = preload("res://building.tscn")

# 1. The script preloads the value, so it will load as a dependency
#    of the 'my_buildings.gd' script file. But, because this is a
#    property rather than a constant, the object won't copy the preloaded
#    PackedScene resource into the property until the script instantiates
#    with .new().
#
# 2. The preloaded value is inaccessible from the Script object alone. As
#    such, preloading the value here actually does not provide any benefit.
#
# 3. Because the user exports the value, if this script stored on
#    a node in a scene file, the scene instantiation code will overwrite the
#    preloaded initial value anyway (wasting it). It's usually better to
#    provide `null`, empty, or otherwise invalid default values for exports.
#
# 4. Instantiating the script on its own with .new() triggers
#    `load("office.tscn")`, ignoring any value set through the export.
@export var a_building : PackedScene = preload("office.tscn")

# Uh oh! This results in an error!
# One must assign constant values to constants. Because `load` performs a
# runtime lookup by its very nature, one cannot use it to initialize a
# constant.
const OfficeScn = load("res://office.tscn")

# Successfully loads and only when one instantiates the script! Yay!
var office_scn = load("res://office.tscn")
```

ការផ្ទុកជាមុន (Preloading) អនុញ្ញាតឱ្យស្គ្រីបដោះស្រាយការផ្ទុកទាំងអស់នៅពេលដែលអ្នកផ្ទុកស្គ្រីប។ ការផ្ទុកជាមុនមានប្រយោជន៍ ប៉ុន្តែក៏មានពេលខ្លះដែរដែលអ្នកមិនចង់ប្រើវា។ ខាងក្រោមនេះគឺជាកត្តាមួយចំនួនដែលត្រូវពិចារណានៅពេលកំណត់ថាតើគួរប្រើមួយណា៖

1. ប្រសិនបើអ្នកមិនអាចកំណត់បានថាពេលណាស្គ្រីបអាចនឹងផ្ទុក នោះការផ្ទុកជាមុននូវធនធាន (ជាពិសេស scene ឬ script) អាចបណ្តាលឱ្យមានការផ្ទុកបន្ថែមដែលអ្នកមិនរំពឹងទុក។ វាអាចនាំឱ្យមានពេលវេលាផ្ទុកដែលមិនបានគិតទុក និងមានប្រវែងផ្លាស់ប្តូរ បន្ថែមលើប្រតិបត្តិការផ្ទុករបស់ស្គ្រីបដើម។
2. ប្រសិនបើអ្វីមួយផ្សេងទៀតអាចជំនួសតម្លៃនោះ (ដូចជាការចាប់ផ្តើមដំណើរការដែលបាននាំចេញរបស់ scene) នោះការផ្ទុកជាមុននូវតម្លៃនោះគ្មានអត្ថន័យទេ។ ចំណុចនេះមិនមែនជាកត្តាសំខាន់ទេ ប្រសិនបើអ្នកមានបំណងបង្កើតស្គ្រីបដោយខ្លួនឯងជានិច្ច។
3. ប្រសិនបើអ្នកចង់តែ 'នាំចូល' ធនធានថ្នាក់ផ្សេងទៀត (script ឬ scene) នោះការប្រើថេរដែលបានផ្ទុកជាមុន ជាញឹកញាប់គឺជាវិធីសាស្ត្រល្អបំផុត។ ទោះជាយ៉ាងណាក៏ដោយ នៅក្នុងករណីលើកលែង អ្នកប្រហែលជាមិនចង់ធ្វើបែបនេះទេ៖
   1. ប្រសិនបើថ្នាក់ដែលបាន 'នាំចូល' អាចនឹងផ្លាស់ប្តូរ នោះវាគួរតែជា property ជំនួសវិញ ដែលត្រូវបានចាប់ផ្តើមដំណើរការដោយប្រើ `@export` ឬ `load()` (ហើយប្រហែលជាមិនទាន់ចាប់ផ្តើមដំណើរការរហូតដល់ពេលក្រោយ)។
   2. ប្រសិនបើស្គ្រីបត្រូវការអាស្រ័យផ្សេងៗជាច្រើន ហើយអ្នកមិនចង់ប្រើប្រាស់អង្គចងចាំច្រើនពេក នោះអ្នកប្រហែលជាចង់ផ្ទុក និងដកការផ្ទុកនូវអាស្រ័យផ្សេងៗនៅពេលដំណើរការ (runtime) នៅពេលដែលកាលៈទេសៈផ្លាស់ប្តូរ។ ប្រសិនបើអ្នកផ្ទុកធនធានជាមុនចូលទៅក្នុងថេរ (constants) នោះវិធីតែមួយគត់ដើម្បីដកការផ្ទុកធនធានទាំងនេះ គឺត្រូវដកការផ្ទុកស្គ្រីបទាំងមូល។ ប្រសិនបើផ្ទុយមកវិញ ពួកវាត្រូវបានផ្ទុកជា properties នោះអ្នកអាចកំណត់ properties ទាំងនេះទៅ `null` ហើយយកចេញនូវការយោងទាំងអស់ទៅកាន់ធនធាន (ដែល ជាប្រភេទដែលពង្រីកពី [RefCounted](https://docs.godotengine.org/en/stable/classes/class_refcounted.html#class-refcounted) នឹងធ្វើឱ្យធនធានលុបខ្លួនឯងចេញពីអង្គចងចាំ)។

### កម្រិតធំៗ (Large levels)៖ static ធៀបនឹង dynamic[](https://docs.godotengine.org/en/stable/tutorials/best_practices/logic_preferences.html#large-levels-static-vs-dynamic)

ប្រសិនបើអ្នកកំពុងបង្កើតកម្រិត (level) ធំមួយ តើកាលៈទេសៈមួយណាដែលសមស្របបំផុត? តើវាល្អជាងក្នុងការបង្កើតកម្រិតនោះជាទំហំ static តែមួយ? ឬតើវាល្អជាងក្នុងការផ្ទុកកម្រិតនោះជាផ្នែកៗ ហើយផ្លាស់ប្តូរមាតិកាពិភពលោកតាមតម្រូវការ?

ចម្លើយសាមញ្ញគឺ "នៅពេលដែលដំណើរការ (performance) តម្រូវឱ្យធ្វើបែបនោះ"។ ការសម្រេចចិត្តដែលទាក់ទងនឹងជម្រើសទាំងពីរនេះ គឺជាការជ្រើសរើសក្នុងការសរសេរកម្មវិធីដ៏ចាស់យូរមកហើយមួយ៖ តើអ្នកគួរធ្វើឱ្យប្រសើរឡើងនូវអង្គចងចាំ (memory) ជាងល្បឿន ឬផ្ទុយមកវិញ?

ចម្លើយដ៏សាមញ្ញបំផុតគឺប្រើកម្រិត static ដែលផ្ទុកអ្វីៗទាំងអស់ក្នុងពេលតែមួយ។ ប៉ុន្តែ អាស្រ័យលើគម្រោង វាអាចប្រើប្រាស់អង្គចងចាំច្រើន។ ការប្រើប្រាស់ RAM របស់អ្នកប្រើប្រាស់ដោយឥតប្រយោជន៍ នាំឱ្យកម្មវិធីដំណើរការយឺត ឬដួលរលំទាំងស្រុង ដោយសារអ្វីៗផ្សេងទៀតដែលកុំព្យូទ័រព្យាយាមធ្វើក្នុងពេលតែមួយ។

មិនថាយ៉ាងណាក៏ដោយ អ្នកគួរតែបំបែក scenes ធំៗទៅជា scenes តូចៗ (ដើម្បីជួយក្នុងការប្រើប្រាស់ធនធានឡើងវិញ)។ អ្នកអភិវឌ្ឍន៍អាចរចនា node មួយដែលគ្រប់គ្រងការបង្កើត/ផ្ទុក និងការលុប/ដកការផ្ទុកនូវធនធាន និង nodes ក្នុងពេលជាក់ស្តែង។ ហ្គេមដែលមានបរិស្ថានធំ និងចម្រុះ ឬធាតុដែលបានបង្កើតដោយនីតិវិធី (procedurally generated) តែងតែអនុវត្តយុទ្ធសាស្ត្រទាំងនេះ ដើម្បីជៀសវាងការប្រើប្រាស់អង្គចងចាំដោយឥតប្រយោជន៍។

ផ្ទុយមកវិញ ការសរសេរកូដប្រព័ន្ធដែលមានលក្ខណៈ dynamic គឺស្មុគស្មាញជាង វាប្រើប្រាស់លោជីខដែលបានសរសេរកម្មវិធីច្រើនជាង ដែលបណ្តាលឱ្យមានឱកាសសម្រាប់កំហុស និង bugs។ ប្រសិនបើអ្នកមិនប្រុងប្រយ័ត្ន ពួកគេអាចអភិវឌ្ឍប្រព័ន្ធមួយដែលធ្វើឱ្យបំពង់បន្ថែមនូវបំណុលបច្ចេកទេស (technical debt) របស់កម្មវិធី។

ដូច្នេះ ជម្រើសល្អបំផុតនឹងគឺ...

1. ប្រើកម្រិត static សម្រាប់ហ្គេមតូចៗ។
2. ប្រសិនបើអ្នកមានពេលវេលា/ធនធានលើហ្គេមមធ្យម/ធំ ចូរបង្កើតបណ្ណាល័យ ឬ plugin ដែលអាចគ្រប់គ្រង nodes និងធនធានដោយប្រើកូដ។ ប្រសិនបើបានកែលម្អតាមពេលវេលា ដើម្បីកែលម្អភាពងាយស្រួលប្រើ និងស្ថេរភាព នោះវាអាចវិវត្តទៅជាឧបករណ៍ដែលអាចទុកចិត្តបាននៅទូទាំងគម្រោងផ្សេងៗ។
3. ប្រើលោជីខ dynamic សម្រាប់ហ្គេមមធ្យម/ធំ ព្រោះអ្នកមានជំនាញសរសេរកូដ ប៉ុន្តែគ្មានពេលវេលា ឬធនធានដើម្បីកែលម្អកូដនោះទេ (ហ្គេមត្រូវតែបញ្ចប់)។ អាចនឹងកែសម្រួល (refactor) នៅពេលក្រោយ ដើម្បីដាក់កូដនោះចូលទៅក្នុង plugin។

សម្រាប់ឧទាហរណ៍អំពីវិធីផ្សេងៗដែលអ្នកអាចប្តូរ scenes នៅពេលដំណើរការ (runtime) សូមមើលឯកសារ ["Change scenes manually"](https://docs.godotengine.org/en/stable/tutorials/scripting/change_scenes_manually.html#doc-change-scenes-manually)។
